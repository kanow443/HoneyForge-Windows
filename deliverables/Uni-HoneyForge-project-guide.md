# Uni — HoneyForge: понятное описание проекта

## 1. Задача

HoneyForge — центр управления учебными ловушками для наблюдения за подозрительной активностью. Вместо ручной настройки каждой приманки оператор создаёт профиль, отправляет его на удалённый сенсор и видит события, сессии, файлы и состояние в одной панели. Это соответствует кейсу «Мадригал. Конструктор» из приложенного PDF. Использовать нужно только принадлежащий команде стенд и синтетические учётные данные.

## 2. Что находится в проекте

| Слой | Назначение |
| --- | --- |
| React/TypeScript | Панель: обзор, профили, хосты, развёртывания, события, дела, доказательства, пользователи, CTF-флаги, интеграции |
| FastAPI | Вход операторов, права доступа, версии профилей, задания сенсорам, приём и выдача данных |
| PostgreSQL | Профили, запуски, события, сессии, аудит, доказательства, пометки, задания и баллы |
| Linux-сенсор | Получает конфигурацию по защищённому каналу, запускает приманки, буферизует события и доставляет их в центр |
| Приманки | Low TCP: баннеры и простые ответы; Medium HTTP/SSH: правдоподобное взаимодействие; High: отдельная настоящая Ubuntu VM при подходящем хосте |
| Gateway | HTTPS, отдельный маршрут `/assets/sync/v1`, разграничение публичного сервиса и управления |
| Локальная очередь | SQLite outbox сохраняет наблюдения при обрыве связи и повторяет отправку; сервер убирает дубли по идентификаторам |

Поток данных: **профиль → задание сенсору → работающая приманка → действие учебного клиента → событие в сенсоре → защищённая доставка → PostgreSQL → SSE и панель**. Публикация новой версии профиля не меняет уже запущенную ловушку без явного повторного применения.

## 3. Основные сценарии

1. Администратор регистрирует сенсор. Оператор создаёт профиль с сервисами, портами, баннерами, фиктивными учётками, файлами и параметрами записи.
2. Оператор выбирает хост и развёртывает профиль. Профиль v3 может объединить 2–8 сервисов; группа запускается, останавливается и повторно применяется вместе.
3. Учебный клиент касается TCP-порта, HTTP-страницы или SSH-приманки. Low отмечает соединение и простые ответы; Medium записывает запросы, ввод, команды и вывод эмулятора.
4. Агент доставляет события. Панель показывает журнал, фильтры, сессии, живое воспроизведение и историю. Статус `pending` команды означает ожидание подтверждения сенсора, а не уже выполненное действие.
5. Аналитик исследует событие, при необходимости раскрывает защищённый фрагмент с аудитом, добавляет пометку, создаёт дело, закрепляет доказательства и экспортирует результат.
6. Оператор может ограничить новые подключения с конкретного наблюдаемого IP к конкретной ловушке. Для SSH отдельно запрашивается завершение текущих транспортов; итог подтверждает агент.

## 4. Роли и доступ

| Роль | Возможности |
| --- | --- |
| Администратор | Все функции; пользователи, подключение и отзыв сенсоров, сертификаты, интеграции, CTF-задания |
| Оператор | Профили, ловушки, реакции, расследования и пометки событий |
| Аналитик | Просмотр, дела, доказательства, экспорт и пометки; без управления ловушками |
| Наблюдатель | Только просмотр обычных разделов; без изменений, экспорта и приватных данных |
| Участник CTF | Только задания, отправка флагов и таблица результатов; без доступа к телеметрии и управлению |

Права проверяются сервером на каждом операторском маршруте. Новые маршруты по умолчанию запрещены, пока им не назначена категория. Изменение роли завершает текущие сеансы пользователя; единственного администратора нельзя понизить.

## 5. Два вида флагов

**CTF-флаг.** Администратор создаёт honeytoken для HTTP или SSH-профиля, применяет профиль к ловушке, дожидается подтверждённого состояния Running и берёт ID текущей привязки на странице профиля. При новом применении в приманочном ресурсе размещается маркер `CTF_FLAG=HF{...}` рядом с `BACKUP_ACCESS_KEY`. Администратор создаёт задание из ID привязки, названия и числа очков. Участник входит с отдельной ролью, находит маркер на учебной приманке и отправляет `HF{...}`. Сервер сверяет значение с конкретной привязкой, начисляет очки один раз на пользователя и задание и показывает таблицу результатов. Отзыв honeytoken, отключение задания или смена поколения ловушки закрывают приём новых решений. Уже начисленные очки остаются историей. Если приманка была развёрнута до добавления строки `CTF_FLAG`, значение `BACKUP_ACCESS_KEY` можно отправить как `HF{значение}`; для явной строки в ресурсе нужно повторно применить профиль.

**Флаг события.** Аналитик, оператор или администратор отмечает запись как «Подозрительно», «Проверено», «Ложное срабатывание» или «Передано на разбор», добавляет пояснение и может снять пометку. Журнал фильтруется по типу пометки. Пометки хранятся отдельно от исходной телеметрии; изменение и снятие записываются в аудит. Несколько разных пометок возможны у одного события.

## 6. Безопасность и маскировка

Центр, доверенный сенсор и недоверенная приманка разделены. Секреты управления, ключи и Docker socket не выдаются приманке. Управляющий трафик идёт по HTTPS; предусмотрены проверка CA/имени, индивидуальные сертификаты клиента и SPKI pinning. Маршрут управления выглядит как обычный веб-путь, а агент запускается под нейтральным именем за пределами приманки. Интервалы и размеры beacon меняются. Реальные пароли и ограниченные payload-фрагменты шифруются до журналов и очереди. При этом обычный PCAP может содержать исходные HTTP-байты, поэтому к нему применяется отдельный доступ. Ни одна из мер не означает абсолютную нераспознаваемость ловушки.

## 7. Доказательства и аналитика

События содержат источник, время наблюдения и приёма, тип, ловушку, поколение и происхождение. SFTP-файлы и PCAP учитываются как артефакты с размером и SHA-256; загрузка идёт с проверкой. Дела объединяют сессии и могут закреплять доказательства от удаления по сроку хранения. Есть honeytokens, пороговые правила обнаружения, IoC CSV/STIX 2.1, локальные City/ASN базы, журнал аудита, JSON-отчёт и интеграционный API. IP и баннер клиента описывают наблюдение, но сами по себе не устанавливают личность или ОС человека.

## 9. Проверки и честные границы

В историческом выпуске сохранены результаты реального стенда: 2 сенсора, 10 ловушек, 9000 уникальных HTTP-событий за 900 секунд без дублей, 8 SSH-сессий, восстановление после 60 секунд потери связи. p95 1,401 с относится к 8078 **видимым DOM-строкам** прежней сборки, а не к каждому событию, физическому paint или внешнему SLA. Более поздние изменения и новые флаги нельзя автоматически считать покрытыми этим прогоном. Для High проверялись настоящая Ubuntu VM, сброс и изоляция с QEMU TCG; KVM на целевом Windows-хосте и внешний продакшн SLA требуют отдельной приёмки. Работающее локальное окружение не доказывает универсальную скрытность от всех детекторов.

## 10. Как показать проект

1. Открыть обзор, показать два удалённых сенсора и состояние ловушек.
2. Показать профиль Low/Medium, версию, сервисы и принцип явного redeploy.
3. С учебного клиента подключиться к Low, затем к SSH/HTTP; открыть новые события и живую сессию.
4. Показать артефакт и совпадение размера/SHA-256, затем дело и пометку события.
5. Показать CTF-маркер в приманочном ресурсе, отправку из роли участника, начисление очков и повторный отказ.
6. Объяснить три контура доверия, очередь при обрыве связи и подтверждение реакции агентом.

Сценарии запуска на Windows: `README_WINDOWS.md` и `START_WINDOWS.cmd`. Перед выступлением использовать адреса и статусы текущего стенда, а не исторические значения из отчётов. Учётные данные панели, ключи агентов и реальные пароли на экране не показывать.
