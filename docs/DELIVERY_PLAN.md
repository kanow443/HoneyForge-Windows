# Последовательность разработки HoneyForge

Каждая задача выполняется последовательно одним ИИ-исполнителем под контролем одного человека. Переход к следующей задаче требует результата, проверки и записи в [журнале](WORKLOG.md). Все задачи приложения сейчас имеют статус «запланировано».

Сначала собирается работающий путь HTTP от панели до удалённой ловушки. После него подключается SSH и завершаются расследование, устойчивость и оформление. Время на высокий уровень и дополнительные протоколы выделяется только после приёмки основного объёма.

## Контрольные точки

| Точка | Задачи | Что уже должно работать |
| --- | --- | --- |
| G1 | T01–T05 | Контракты, БД, защищённая sensor VM, зарегистрированный агент |
| G2 | T06–T09 | Из панели запущена HTTP-приманка на другой VM, её реальное событие видно и stop работает |
| G3 | T10–T13 | SSH-сессия, конструктор, восстановление потока и объяснимый анализ |
| G4 | T14–T17 | Полный UX, проверки сбоев, воспроизводимый запуск, доказательства и демо |

Это план зависимости, а не план одновременной работы нескольких людей. Для неизвестного дедлайна резервировать примерно последнюю четверть доступного времени на G4. При нехватке времени убирать P1/P2, сохраняя удалённый запуск, оба уровня, сбор, историю, анализ и демонстрацию.

## T01 Основа проекта и договорённости

**Зависимости:** нет. **Результат:** каркас `apps/web`, `services/control`, `services/agent`, `infra`, тестовый запуск API и UI, схема контрактов v1 и lock-файлы. Локальную историю Git создать, если её ещё нет; исходные документы сохранить.

**Действия:** закрепить версии; создать модель событий, профилей, заданий и ошибок; описать IDs и состояния; добавить `.env.example` без секретов; подготовить Compose управления и одну команду локального запуска; выбрать способ запуска учебных VM. HTTPS и bootstrap включить в план окружения.

**Зачем:** интерфейс и агент должны использовать одну модель, чтобы ИИ не придумал несовместимые структуры на разных этапах.

**Приёмка:** UI открывается; health API отвечает; OpenAPI выгружается; пример профиля проходит валидацию, неизвестный adapter отклоняется. **Доказательства:** схема v1, версии зависимостей и журнал запуска `docs/evidence/T01/`.

## T02 Технический прототип адаптеров

**Зависимости:** T01. **Результат:** проверенная таблица возможностей HTTP и закреплённого Cowrie shell backend.

**Действия:** в закрытом учебном окружении проверить запуск Cowrie, журнал JSON, session ID, события команд, способ применения hostname/баннера/фиктивных файлов; проверить совместимость read-only filesystem и каталоги записи. Создать минимальный прототип HTTP-ответа и JSON-журнала. Сверить поля конструктора с тем, что реально поддерживается.

**Зачем:** не проектировать UI вокруг настроек, которые невозможно применить. **Приёмка:** две контролируемые SSH-команды читаются из журнала; HTTP-запрос даёт структурированное событие; список настроек подтверждён. **Доказательства:** очищенные образцы событий, конфигурация и таблица поддерживаемых полей `T02/`. Это прототип, не готовая интеграция.

## T03 Sensor VM и сетевой контур

**Зависимости:** T01, T02. **Результат:** отдельная Linux VM, bootstrap, закреплённый Docker, политика сети и лимиты.

**Действия:** создать/подключить учебную VM, отделённую от управления; выделить сети и порты; запретить новые исходящие соединения ловушек и доступ к управлению/соседям; закрыть управляющие сервисы; проверить IPv6; включить ограничения контейнеров и журнал сетевых отказов. Подготовить bootstrap, systemd unit и тестовый network probe.

**Зачем:** компрометация атакуемого сервиса не должна открывать доступ к управлению. **Приёмка:** разрешённые входящие подключения работают; сетевые probes к API, БД, host services, LAN и внешнему контрольному адресу не проходят; исходный IP учебного клиента сохранён; ресурсные пределы действительно действуют. **Доказательства:** схема адресов, безопасная конфигурация, результаты probes, версии runtime `T03/`.

Наличие Docker Desktop на Mac не заменяет приёмку на целевом Linux-хосте. Если удалённой VM пока нет, подготовить bootstrap и локальный изолированный стенд, отметить внешний запуск как ожидающий окружения; не объявлять R03 выполненным.

## T04 База управления и авторизация

**Зависимости:** T01. **Результат:** миграции, модели профилей/версий, deployments/jobs, audit и сессия оператора.

**Действия:** создать типизированные таблицы и ограничения; хранить password hash; выдавать HttpOnly Secure cookie через HTTPS; добавить CSRF-защиту изменяющих запросов, ограничение попыток входа и единый обработчик ошибок; публиковать версии профиля неизменяемо. Экспорт и SSE используют ту же проверку пользователя.

**Зачем:** история должна сохранять точную конфигурацию, а управление — иметь явную границу доступа. **Приёмка:** новая версия не меняет старую; без авторизации данные недоступны; logout отзывает сессию; миграции применяются на чистой БД. **Доказательства:** результат интеграционных проверок с настоящей PostgreSQL `T04/`.

## T05 Регистрация и состояние агента

**Зависимости:** T03, T04. **Результат:** одноразовая регистрация, индивидуальный ключ, heartbeat и revoke.

**Действия:** обменивать enrollment token с TTL на ключ хоста; хранить hash ключа на сервере и файл 0600 на VM; передавать capabilities, runtime version, наблюдаемые состояния, ресурсы и счётчики очереди. Агент инициирует HTTPS-соединения. В API связать каждый ключ с одним хостом.

**Зачем:** агент не должен выдавать себя за другой хост или пользоваться общим администраторским ключом. **Приёмка:** использованный/просроченный enrollment token отклонён; подмена host ID отклонена; revoke прекращает новые задания; просроченный heartbeat даёт offline/unknown. **Доказательства:** ответы API с очищенными секретами, снимок хоста `T05/`.

## T06 HTTP адаптер и профиль

**Зависимости:** T02–T05. **Результат:** низкоинтерактивная HTTP-приманка, два различимых профиля и общий интерфейс адаптера.

**Действия:** реализовать фиксированную страницу, разрешённые заголовки, фиктивные пути, безопасные синтетические данные; логировать метод, путь, источник, время и response status; исключать секретные поля. Проверять профиль на сервере и в агенте. Конфигурация read-only, каталог логов ограничен.

**Зачем:** быстро получить настоящий управляемый сервис, пригодный для первого сквозного сценария. **Приёмка:** профили дают ожидаемые различимые ответы; неизвестные параметры отклонены; событие содержит deployment/runtime identity; лимиты размера применены. **Доказательства:** ответы HTTP и образцы JSON `T06/`.

## T07 Задания deploy и stop

**Зависимости:** T04–T06. **Результат:** durable jobs, lease, попытки, reconcile и фактические статусы.

**Действия:** транзакционно создавать deployment/job/port reservation/audit; проверять ключ идемпотентности; применять adapter по labels; возвращать этапы и очищенную ошибку; проверять readiness; сериализовать операции по deployment; восстанавливаться после перезапуска.

**Зачем:** успешный HTTP-запрос к API ещё не означает, что удалённый сервис работает. **Приёмка:** deploy через API запускает один контейнер; повтор не создаёт второй; занятый порт даёт error; stop удаляет runtime, история сохраняется; старый результат job не меняет новую revision. **Доказательства:** API result, labels runtime и проверки гонок `T07/`.

## T08 Очередь и приём событий

**Зависимости:** T06, T07. **Результат:** источник → SQLite outbox → PostgreSQL с ACK и дедупликацией.

**Действия:** атомарно сохранять событие и cursor источника; учитывать ротацию; повторять batches с backoff; подтверждать после commit; отделять quarantine; включить квоты и счётчики потерь; создать session/event нормализацию.

**Зачем:** события не должны исчезать при кратком обрыве или учитываться несколько раз. **Приёмка:** после 60 с недоступности API накопленные события доставлены; повтор тех же IDs не меняет count; аварийное завершение агента между read/ACK не создаёт потерь в пределах очереди. **Доказательства:** сверка отправленных и сохранённых IDs, отчёт перезапуска `T08/`.

## T09 Первый законченный сценарий в панели

**Зависимости:** T07, T08. **Результат:** тонкий UI входа, профиля HTTP, выбора хоста, deploy/status/stop и списка событий.

**Действия:** подключить реальные API; построить единый layout; показать фактический статус и ошибки; добавить минимальную форму и подробности события. До T12 разрешено обновление списка коротким polling с честным обозначением состояния.

**Зачем:** рано проверить связь продукта, агента и хранения. **Приёмка:** человек выполняет HTTP-сценарий из браузера на отдельной VM; после stop новый запрос не обслуживается; старое событие остаётся. **Доказательства:** короткая запись экрана, event ID и deployment ID `T09/`. Это точка G2.

## T10 SSH адаптер Cowrie

**Зависимости:** T02, T08, T09. **Результат:** второй adapter с общей системой профилей, заданий и событий.

**Действия:** встроить закреплённый Cowrie shell backend; переводить session/login/command события в общий контракт; учитывать runtime generation; ограничить фиктивные файлы и пути; отключить ненужные функции передачи файлов или ограничить карантин. Конкретный digest и конфигурацию сохранить.

**Зачем:** показать другой уровень взаимодействия и расширяемость архитектуры. **Приёмка:** контролируемый вход и две команды дают одну корректную сессию; повторные строки не дублируются; новая runtime generation не смешивается со старой сессией. **Доказательства:** очищенная SSH-сессия, raw→normalized mapping `T10/`.

## T11 Конструктор и версии профилей

**Зависимости:** T09, T10. **Результат:** полный путь шаблон → легенда → ресурсы → обзор → публикация → deployment.

**Действия:** реализовать поля согласно T02; сравнение версий; предпросмотр поддерживаемых ответов без запуска чужого кода; server-side validation; список compatible hosts; конфликт портов и offline host. Версию и image digest показывать на deployment detail.

**Зачем:** настройка должна быть доступна оператору без ручного редактирования конфигураций. **Приёмка:** два опубликованных профиля применяются на одном хосте; новая версия не меняет запущенный runtime; invalid field показывает причину рядом с полем. **Доказательства:** снимки формы, response/version IDs `T11/`.

## T12 Живой поток и восстановление UI

**Зависимости:** T08, T09. **Результат:** SSE, commit-safe stream cursor, snapshot/replay, reconnect/reset.

**Действия:** записывать event_stream в транзакции; назначать курсор под row lock; подключить cookie auth; сохранять cursor; обрабатывать filter reset, retention reset, паузу UI и ограниченный буфер. Проверить proxy buffering.

**Зачем:** «реальное время» должно работать и после обрыва, а список не должен пропускать поздний commit. **Приёмка:** конкурентные транзакции не теряют события; reconnect дочитывает разрыв без дублей; refresh страницы получает согласованный snapshot; неавторизованный stream запрещён; p95 измерен. **Доказательства:** trace потока и результат измерения `T12/`.

## T13 Анализ и просмотр сессий

**Зависимости:** T10–T12. **Результат:** timeline, фильтры, findings с объяснениями и экспорт JSON.

**Действия:** реализовать версионируемые правила по событиям; сохранять evidence IDs; отличать intent эмулятора от реального network observation; отображать session source, command sequence и временную шкалу; экспортировать параметры выборки, версии и hash. Не объединять людей по одному IP.

**Зачем:** журнал становится инструментом разбирательства. **Приёмка:** положительные и отрицательные наборы дают ожидаемые findings; объяснение ссылается на реальные события; экспорт повторно читается и совпадает с выбранной сессией; пароли не попадают в UI. **Доказательства:** тест правил и экспорт учебной сессии `T13/`. Это точка G3.

## T14 Завершение UI

**Зависимости:** T11–T13. **Результат:** единая визуальная система по [UI-плану](UI_REFERENCES.md).

**Действия:** доработать таблицы, фильтры, detail panel, deployment steps, overview; добавить empty/loading/error/offline/degraded состояния; проверить клавиатуру, контраст и размеры окна. Анимации ограничить полезными переходами.

**Зачем:** оператор должен быстро понимать, что работает, что произошло и какое действие доступно. **Приёмка:** ключевой сценарий выполняется без скрытых действий; статус есть текстом; при высокой активности таблица не прыгает; детали сохраняют контекст фильтра; логи не исполняют HTML/ANSI. **Доказательства:** скриншоты всех состояний и browser walkthrough `T14/`.

## T15 Проверки сбоев и ограничений

**Зависимости:** T03–T14. **Результат:** отчёт обязательных проверок из [плана продукта](PRODUCT_PLAN.md).

**Действия:** проверить сеть, IP, падение API и агента, повторы, ротацию, lease expiration, deploy/stop race, заполнение квоты, невалидный batch, XSS/ANSI, path traversal/symlink в профиле и журналах, отзыв ключа, auth экспорт/stream. Провести короткий прогон при 10 событиях/с и зафиксировать p95 и счётчики.

**Зачем:** доказать конкретные свойства системы, которые будут обсуждаться на защите. **Приёмка:** обязательные проверки прошли либо недостатки исправлены и перепроверены; никаких выдуманных pass и производительности. **Доказательства:** отчёт с expected/actual, конфигурацией и артефактами `T15/`.

## T16 Воспроизводимая сборка и запуск

**Зависимости:** T15. **Результат:** release snapshot, инструкция, seed/demo reset и предварительно загруженные образы.

**Действия:** поднять управление с чистого состояния; зарегистрировать чистый агент; применить миграции; выполнить сценарий; сохранить версии/образные digest; подготовить очистку только учебных данных. Установить TTL для enrollment и отдельный demo user.

**Зачем:** демо должно повторяться без ручного восстановления случайного локального состояния. **Приёмка:** другой запуск по инструкции воспроизводит сценарий; reset не затрагивает чужие контейнеры или данные; секретов в docs/logs нет. **Доказательства:** инструкция и журнал чистого запуска `T16/`.

## T17 Защита и фиксация результата

**Зависимости:** T16. **Результат:** пять смысловых слайдов, демонстрация на 4–5 минут, резервное видео и таблица фактических результатов.

**Действия:** заполнить [сценарий защиты](DEFENSE.md) по настоящим evidence; провести две репетиции; проверить отображение на проекторе; зафиксировать build/revision, профиль и event IDs. Подготовить короткие ответы про Cowrie, изоляцию, уровни, доставку и масштабирование.

**Зачем:** объяснить собственный вклад и решения понятным языком, подкрепляя их работой системы. **Приёмка:** демонстрация проходит дважды подряд; все цифры имеют evidence; ограничения явно совпадают с реализованным объёмом. **Доказательства:** видео, presentation artifact, окончательная таблица покрытия `T17/`. Это точка G4.

## T18 Высокий уровень взаимодействия при необходимости

**Зависимости:** завершённый P0, доступный VM-runtime, время на отдельную приёмку. **Результат:** отдельный adapter Cowrie proxy с одноразовым backend VM.

**Действия:** вынести гостевую ОС за отдельную границу; ограничить сеть снаружи; не помещать agent credentials внутрь; настроить snapshot/reset и лимиты времени; проверить наблюдение и очистку. Обновить ADR и UI capability matrix.

**Приёмка:** выполняется контролируемая команда в реальной гостевой ОС; гостю недоступны управление/LAN/внешние адреса; после reset изменения удалены; события сохраняются. **Доказательства:** схема VM, результаты сети и reset `T18/`. До этого в UI доступны только low и medium.

## Что снимать с объёма при нехватке времени

Сначала дополнительные протоколы и GeoIP, затем второй хост, расширенный отчёт и откат. Нейросети и AI API исключены из продукта по требованию пользователя. Высокий уровень снимается только если не является обязательным по правилам. Визуальную полировку сокращать до одной последовательной темы, сохраняя ошибки, offline, пустые состояния и читаемую таблицу. Сетевую изоляцию, авторизацию и честность статусов не переносить в «после защиты».
