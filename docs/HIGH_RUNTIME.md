# High: настоящая ОС и автоматический сброс

> Архивный документ прежней сборки. В текущей версии HoneyForge поддержка High
> удалена из исходного кода, API, интерфейса и сенсора. Приведённые ниже команды
> больше не применяются; актуальный запуск описан в [README_WINDOWS.md](../README_WINDOWS.md).

High — отдельный бонусный адаптер `cowrie-high` (profile schema v2, также разрешён внутри bundle v3). Он использует закреплённый Cowrie 3.1.1 как SSH-прокси и наш внешний пул QEMU. Гость — официальная Ubuntu Minimal 24.04; изображение проверяется по SHA-256 официального HTTPS-каталога и локально повторно перед запуском. Пул написан нами: ограниченный Unix socket между доверенным прокси и доверенным агентом, один qcow2 overlay **на SSH-транспорт**, новый после каждого подключения, без повторного использования по IP.

## Установка

1. Сначала установить и зарегистрировать обычный выделенный Ubuntu 24.04 сенсор по основному руководству. Обновить источник и закреплённый Cowrie-образ. На сенсоре должны работать Docker, firewall и asset-sync.
2. Рекомендуется x86_64/ARM64 Linux с `/dev/kvm`, минимум 4 CPU, 8 GB RAM, 15 GB свободного диска. Не размещать пул на машине с рабочими пользовательскими данными. Для KVM: `sudo bash /opt/asset-sync/scripts/install-high.sh`.
3. Если KVM нет, разрешён **явно выбранный** лабораторный режим: `sudo bash /opt/asset-sync/scripts/install-high.sh tcg`. Это та же настоящая ОС, но программная эмуляция CPU; загрузка и команды медленнее. Наличие KVM/вложенной виртуализации зависит от компьютера и гипервизора.
4. Дождаться `cowrie-high` в возможностях сенсора. Если проверка образа/хоста не прошла, эта capability не публикуется, API отклоняет развёртывание.
5. Создать профиль High, выбрать совместимый хост и незанятый порт, развернуть. `Running` означает готовность прокси. Гостевая ОС стартует при первом соединении; первое открытие shell может занимать до 240 секунд в KVM / 600 секунд в TCG; в TCG SSH-клиенту нужен увеличенный timeout.
6. Войти учёткой-приманкой профиля, например `ssh -p 18622 root@SENSOR_IP` (пароль из профиля). Backend-учётка `root/asset-guest-demo` — исключительно синтетическая учётка гостя, не учётка центра/сенсора.

## Что происходит

- Агент проверяет baseline, создаёт overlay и cloud-init seed, запускает QEMU от отдельного `asset-guest` без root, с seccomp, двумя vCPU (настраивается оператором), заданной RAM и лимитами файлов/дескрипторов.
- QEMU предоставляет гостю виртуальную сеть `restrict=on`, без новых исходящих соединений к Интернету/сенсору/центру/соседям. SSH backend привязан только к gateway отдельного bridge ловушки; firewall добавляет исключение ровно на его порт для этого bridge.
- В госте нет Docker socket, каталогов агента, ключей management, библиотек HoneyForge и управляющего канала. Прокси получает только публичный ключ запечатанной записи и синтетические параметры.
- Cowrie фиксирует ввод, а наш hook передаёт реальный вывод гостевой ОС в существующий плеер; SFTP захватывается протокольным наблюдателем Cowrie. Файлы не исполняются центром.
- При закрытии SSH-транспорта агент останавливает QEMU, удаляет разрешение firewall и весь изменяемый диск. Независимые одновременные сессии не разделяют ОС.
- Аварийный перезапуск агента удаляет оставшиеся гости/диски (PID проверяется по uid и точному пути диска), затем восстанавливает прокси через reconciler. Baseline не перезаписывается. Сессии аварийного перезапуска завершаются.

## Границы

Максимум 2 сессии на ловушку, общий предел процесса агента 4 гостя, 30 минут на гостя, 2 GiB на изменяемый файл диска. Новые подключения при заполнении пула отклоняются, ничего не разделяется со старым гостем. Выход в Интернет закрыт; `wget/curl` в High не скачивает произвольные файлы. Baseline и настройки гипервизора обслуживает доверенный оператор; захват самого гипервизора исключён моделью угроз. Мы не гарантируем нераспознаваемость Cowrie/QEMU и не называем TCG производительностью KVM.

Проверка для защиты: реальный `/etc/os-release`, `ps`, собственный файл в `/root`, закрытие транспорта, новое соединение → файл отсутствует; параллельные сессии → разные процессы/диски; TCP к внешнему/management/соседу не проходит; ввод/вывод виден в плеере; SFTP SHA совпадает. Актуальные результаты лежат в `docs/evidence/backend/high-real-os.json`, когда проверка завершена. Само наличие этой инструкции не является доказательством прогона.

Основание протокольного режима: https://docs.cowrie.org/en/stable/PROXY.html. Альтернатива upstream pool: https://docs.cowrie.org/en/stable/BACKEND_POOL.html (выдаёт по IP; здесь выбран отдельный гость на транспорт).


## Проверено на этом стенде

`high-real-os.json`: две отдельные SSH-сессии; Ubuntu 24.04.5 / Linux 6.8 / systemd
и настоящие процессы. Файл `/root/hf-reset-marker` записан первым транспортом, отсутствует
во втором. Подключения к внешнему IPv4 и соседнему сенсору отклонены. TCG/ARM64,
сенсор 4 CPU/6 GiB; первое выполнение 98.98 и 88.79 секунды вместе с командами проверки.
Это конкретный локальный результат, не производительность KVM или внешнее обещание.
Лимиты профиля управляют контейнером доверенного прокси; ресурсы QEMU задаёт оператор
в `HF_HIGH_MEMORY_MB`, `HF_HIGH_VCPUS`, `HF_HIGH_MAX_SESSIONS`. Admission проверяет
cgroup memory и резерв управления, общие резервации защищены от параллельных cold boots.
Ни один управляющий ключ не включается в cloud-init. Hostname, decoy_files и file
honeytokens создаются cloud-init в каждом новом госте.

`high-files.json`: hostname и decoy files применены к настоящему гостю, file token прочитан
и атрибутирован, SFTP 53 байта доставлены в центр и скачаны с совпадающим SHA-256;
реальный stdout сохранён в плеере. После закрытия нет оставшегося QEMU/overlay/firewall порта.
