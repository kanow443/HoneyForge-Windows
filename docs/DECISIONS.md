# Архитектурные решения HoneyForge

Реестр решений базового проекта. Актуальные изменения T01–T24 перечислены ниже. Их причины и компромиссы сформулированы заранее, чтобы на защите объяснять выбор. При техническом прототипе решение может измениться: тогда новая запись ссылается на старую и описывает основание. Наличие записи не означает, что компонент уже реализован.

## Реестр решений

| ID | Решение | Почему выбрано | Альтернатива и компромисс | Проверка |
| --- | --- | --- | --- | --- |
| ADR01 | Модульный FastAPI backend | Для одного исполнителя один контракт и одна транзакционная граница проще поддерживаются | Микросервисы дадут независимое масштабирование, но добавят сетевые отказы и согласование схем | T01, T04; модули имеют собственные обязанности |
| ADR02 | React и TypeScript, Vite, готовые UI-примитивы | Панель состоит из форм, таблиц и подробностей; типы снижают расхождения с API | SSR-фреймворк нужен при требованиях SSR; здесь операторский интерфейс не требует публичного SEO | T09, T14; реальные API и проверка браузером |
| ADR03 | PostgreSQL для управления и событий | Версии, задания и события должны сохраняться согласованно; реляционные колонки плюс JSONB покрывают MVP | ClickHouse/Elastic полезны при измеренной большой аналитической нагрузке; добавляют отдельное хранилище | T04, T15; миграции, фильтры и нагрузочный прогон |
| ADR04 | Pull-agent по исходящему HTTPS | Не требуется открывать управляющий порт sensor VM или передавать SSH-доступ каждому deploy | Server-side SSH даёт быстрый прототип, но требует управления ключами и связывает API с привилегированными командами | T05, T07; ключ ограничен одним хостом, задания сохраняются |
| ADR05 | Две VM и доверенный локальный executor | Атакуемый сервис отделён от БД и панели; полномочия Docker остаются внутри sensor VM | Контейнеры на VM управления дешевле, но объединяют границы риска; дополнительная VM требует настройки | T03, T15; сеть и отсутствие secrets/socket в ловушках |
| ADR06 | В P0 Docker на sensor VM, контейнеры non-root | Сетевой контур и исходный IP проверяются на конкретной конфигурации; agent/runtime считаются доверенными | Rootless требует дополнительной проверки port forwarding, IP и cgroups; его нельзя принимать по названию | T02, T03; лимиты и адрес источника |
| ADR07 | Настоящий Low TCP и Medium HTTP/Cowrie shell | Покрывают разные уровни и дают наблюдаемый пользовательский сценарий | Собственная реализация SSH сложнее и рискованнее; high interaction требует отдельной VM-границы | T06, T10; не переименовывать эмуляцию в настоящую ОС |
| ADR08 | Существующий Cowrie и свой orchestration слой | Использовать проверяемый протокольный компонент, сосредоточив вклад на управлении, профилях, доставке и UX | Собственный SSH engine может стать отдельным проектом; dependency нужно закрепить и указать происхождение | T02, T10; mapping логов и документированный вклад |
| ADR09 | Неизменяемые версии профилей | Для каждого события известна применённая конфигурация; редактирование не меняет историю | Изменяемый JSON быстрее начать, но теряет воспроизводимость; версионирование добавляет таблицу и UI | T04, T11; старый deployment сохраняет прежнюю версию |
| ADR10 | Durable jobs, lease и reconcile | Процесс deploy переживает рестарт; повтор не создаёт второй runtime | Фоновая coroutine без БД проще, но исчезает вместе с API; lease не гарантирует единственное исполнение | T07, T15; идемпотентность, fencing и гонка stop |
| ADR11 | SQLite outbox и ACK после commit | Короткий отказ сети не уничтожает наблюдения; очередь не зависит от работающей БД управления | Прямая отправка проще, но теряет данные; локальный диск и quota остаются границей гарантии | T08, T15; падение до/после ACK, ротация, квота |
| ADR12 | At least once и unique event ID | Повторяемая доставка без повторного учёта реалистична и проверяема | Обещание exactly once во всей системе не учитывает источник, диск и транспорт | T08, T15; сверка ID и повтор 100 событий |
| ADR13 | SSE и долговечный replay | Панели нужны обновления от сервера; команды идут HTTP; пропущенная история хранится в БД | WebSocket нужен при двустороннем потоке; polling допустим на раннем этапе, затем замещается | T12; reconnect, snapshot, concurrent commits |
| ADR14 | Сериализация stream cursor в транзакции | Курсор не должен перескочить через поздно закоммиченный меньший ID | BIGSERIAL удобен для PK, но не задаёт commit order; блокировка ограничивает throughput, который надо измерить | T12, T15; две конкурентные транзакции в обратном порядке |
| ADR15 | Версионируемые аналитические правила | Каждое заключение можно объяснить конкретными events и проверить отрицательным примером | LLM может дать красивый текст, но вносит недетерминированность и риск следования данным атакующего | T13; evidence IDs, пороги, проверка false positives |
| ADR16 | Собрать доказательства вместе с кодом | Защита рассказывает о фактах; журнал позволяет объяснить каждое решение и изменение | Восстановление истории в конце занимает время и приводит к неподтверждённым заявлениям | Каждая T-задача; commit/diff, проверка и артефакт |

Технические основания режимов Cowrie, SSE, Docker и PostgreSQL приведены рядом с соответствующими решениями в [архитектуре](ARCHITECTURE.md). Выборы и границы объёма — инженерное предложение для этого задания, а не утверждение, что существует единственный правильный стек.

## Условия пересмотра

Если полный регламент требует все три уровня, ADR07 расширяется T18. Если среда запрещает агент, ADR04 пересматривается с новым способом remote deployment. Если тест IP или сети не проходит, ADR06 не считается принятым до исправления. Если PostgreSQL не выдерживает фактическую нагрузку/retention, ADR03 пересматривается на основе профилирования. Если появляется второй разработчик, границы модулей уже позволяют разделить работу без немедленного перехода к микросервисам.

## Реализованные решения LIVE-итерации — 10 октября 2026

- ADR17 — отдельная ingestion position и snapshot/replay по watermark. Порядок доставки отличается от observed_at/source_seq: поздние наблюдения должны попадать в догрузку, затем отображаться в правильном порядке. Миграция 003 заполняет позиции сохранённой истории. Проверены страницы, позднее событие, повторы и сброс некорректного курсора.
- ADR18 — scoped source policy с desired/observed revision, ACK и локальным TTL. Политика сохраняется до применения, ограничивает NEW только на bridge одной ловушки, после перезапуска восстанавливается и снимается локально по сроку. Полная изоляция машины/завершение established-сессий не реализуются этим действием. Проверены реальное сетевое запрещение, другой HTTP endpoint, управление, restart и 60с offline.
- ADR19 — отдельный collector thread и SQLite RLock. Медленная сеть не останавливает сбор; atomic event/cursor и seen сохраняют идемпотентность. Проверены параллельные collect/ACK и 1100 событий с одинаковой меткой времени за несколько циклов.
- ADR20 — ограниченный захват настоящего Cowrie shell output через адаптер закреплённого образа. В upstream проверена точка вывода протокола; фрагменты публикуются тем же session EventLog. UTF-8 decoder, coalescing и квоты сохраняют понятный текст при ограниченной памяти. Не включаются LLM и произвольное исполнение ОС клиента. Реальная сессия содержит команды и synthetic file output; автоматические проверки покрывают UTF-8, квоту и очистку последовательностей. При обновлении Cowrie нужна новая runtime-приёмка.
- ADR21 — investigation case с optimistic revision и канонический report. Дело хранит выбор сессий, status/note и audit, конфликт не перетирает чужие изменения. Отчёт включает exact profile/evidence/quality/policy snapshot; Pydantic-normalized JSON сначала канонизируется, затем хешируется, чтобы фактическая UTC/UTF-8 сериализация совпала с hash. SHA-256 не называется цифровой подписью.
- ADR22 — короткие polling-интервалы для локального LIVE и backoff ошибок. После измеренного p95 2.1с успешный upload/main/collector cadence уменьшен до 250мс, jitter до 100мс, SSE query cadence до 250мс; offline backoff остаётся до 15с. Компромисс — больше запросов/проверок; доказательство относится к одному локальному сенсору и одному наблюдателю, не к production-масштабу.

Поведение каждого действия: [USER_GUIDE_RU.md](USER_GUIDE_RU.md). Фактические измерения: [live-lab.json](evidence/backend/live-lab.json). История исходного плана выше сохранена и сама по себе не является доказательством выполнения.
